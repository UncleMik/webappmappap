# Фронтенд на домене школы

Основной адрес: https://app.legkie-rody.ru/.
Прежний адрес https://129.101.119.250/ сохранён.
Каталог сервера: `/opt/wep_pril/frontend/`. Исходники остаются в `Фронт/`.
Фронтенд размещён на сервере. Проверенные изменения публикуются автоматически по правилу из AGENTS.md, без повторного запроса согласия.

## Подготовка

Из корня проекта:

```powershell
python tools/package-frontend.py данные/frontend-release/frontend.zip
```

Архив содержит только страницы, стили, JavaScript и ресурсы интерфейса.
Документы, локальный сервер, настройки пакета, база и оригиналы статей не входят.
API и изображения используют HTTPS домена школы. При открытии по IP
используется API того же IP для совместимости прежних ссылок.
Конфигурация домена — `deploy/nginx-domain.conf`, IP — `deploy/nginx.conf`.
На сервере они установлены отдельно как `wep-pril-domain` и `wep-pril`.
Сертификат домена обновляет существующий `wep-pril-certificate.timer`;
Certbot проверяет оба сертификата и перечитывает nginx после обновления.

18 октября на домене приложения подключён отдельный маршрут `/api/auth/`
к службе входа на `127.0.0.1:3001`; остальные `/api/` идут в сервис статей
на порту 3000. Маршрут сохранён в `nginx-domain.conf`, чтобы обновление
фронтенда его не удалило. Через публичный HTTPS проверен ответ
`503 auth_unavailable` при `AUTH_ENABLED=false`; рабочий вход ещё не включён.

## Публикация после проверок

1. Сверить текущую конфигурацию nginx и сохранить её резервную копию.
2. Загрузить архив в приватный каталог `/opt/wep_pril/deploy/`.
3. Создать `/opt/wep_pril/frontend/`, распаковать архив туда и дать nginx
   чтение файлов и проход по каталогам. Если сайт уже размещён, перед заменой
   сохранить предыдущую версию фронтенда для отката.
4. Установить `deploy/nginx.conf` в используемый конфигурационный файл nginx.
5. Для домена установить `deploy/nginx-domain.conf` в
   `/etc/nginx/sites-available/wep-pril-domain`. Выполнить `nginx -t`, затем
   `systemctl reload nginx` только при успехе.
6. Проверить HTTPS, главную страницу, переходы, статьи и картинки в браузере
   на мобильной ширине. Проверить API, 404 для базы и оригиналов картинок.
7. Обновить GitHub и проверить GitHub Pages после завершения публикации.

При ошибке вернуть сохранённую конфигурацию и предыдущий фронтенд,
проверить `nginx -t` и перечитать конфигурацию. API, SQLite и uploads
при публикации фронтенда не заменяются.

Отметки чтения и выбранная неделя хранятся в браузере отдельно для каждого
адреса: состояние GitHub Pages автоматически на адрес по IP не переносится.
