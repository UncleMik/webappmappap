## Общая архитектура и договорённости

- Сохраняем Node.js и существующую PostgreSQL для пользовательского состояния. Каталог и права GetCourse остаются действующими. Не вводить отдельный сервис, БД или копию аккаунтов.
- Сохраняем существующий auth_points_ledger и подробную историю; расширяем его для отрицательных операций и типов событий. Не суммировать старый баланс второй раз при миграции. Старые награды не менять.
- Все операции только после серверной сессии и сверки X-Webpril-Account. Параллельные списания и повтор запросов должны быть безопасны. Не принимать от клиента сумму награды, факт покупки курса, прошедшие дни или право доступа.
- Суточные начисления учитывают только перечисленные capped события, без расходов и бонусов; 100/150, без недельного ограничения. Нулевой/частичный результат завершает материал для будущих наград, прогресс сохраняется.
- Фича-флаги, подтверждение контента и этап запуска — часть реализации. Не отдавать правильный ответ мифа до ответа, закрытые материалы через новые API или чужие личные данные в админке.
- Нужны полноценные действия и тесты, не только пустые каркасы. При выключенной новой системе действующие сценарии сохраняются. Новые ограничения не отнимают подтверждённые старые права; при неполной истории для legacy аккаунта замки не включаются.

## Общий контракт между тредами

В начале работы каждый тред должен записать уточнённые экспортируемые методы/форматы в `docs/gamification/handoffs/<owner>.md`. По ним другие треды подключают модуль. При изменении контракта обновлять этот файл сразу.

### stars-core.mjs (wallet)

Экспорт `createStars({ pool, service, courseMaterials, settings, catalog, clock })`. Фабрика возвращает:

- `withAccount(token, expectedAccount, callback)` — проверка действующей сессии и аккаунта, затем транзакция и блокировка пользовательского кошелька; callback(client, context). context содержит userId, profile, tier (free/course), currentWeek, moscowDay, now, legacy, pointsEnabled и доступные настройки. Внешнюю проверку курса выполнять до удержания транзакции.
- `credit(client, context, { code, ref, amount, capped, metadata })` — идемпотентное начисление по серверному событию; возвращает actualAmount, balance, duplicate, limited. Проверка факта события остаётся у вызывающего серверного модуля.
- `debit(client, context, { code, ref, amount, metadata })` — идемпотентное списание с проверкой баланса. Покупка и выдача возможности в одной транзакции.
- `wallet(client, context)` — balance, dailyLimit, dailyEarned, dailyRemaining, recent history.
- `completeMaterial(client, context, { kind, id, week, eligibleForReward })` — разовый прогресс и награда, закрытие недели при всех доступных материалах; возвращает progress/reward/letter события.
- `state(token, expectedAccount)` — кошелёк, прогресс по неделям, купленные недели и кредит AI. `purchase(token, expectedAccount, { kind, requestId, week })` — kind=peek_next_week/ai_pack. Без произвольной цены клиента.

Точные имена можно минимально адаптировать по найденному коду, но синхронно зафиксировать в handoff до того, как другие треды начнут интеграцию. Покупку AI и остаток согласовать с access-ai; не создавать два разных хранилища одного и того же остатка.

### gamification.mjs (daily)

Экспорт `createGamification({ pool, service, stars, settings, catalog, notifications, clock })`. Методы `state(token, account)`, `action(token, account, body)`, `preferences(token, account, body)`, `letters(token, account)`, `notifyMaterialComplete` при необходимости. Все мутации через серверную проверку и общий wallet lock.

GET `/api/auth/gamification` отдаёт объединённое состояние: accountId, enabled, tier, currentWeek, pregnancyDay, wallet, today, weeks, features, preferences, letters, quests, capsule, settings для отображения (только публичные). Новая оболочка не должна дублировать полные тексты закрытых будущих материалов.

POST `/api/auth/gamification/actions`: серверный whitelist type `checkin`, `surprise`, `myth_answer`, `quest_done`, `checklist_update`, `first_kick`, `capsule_save`, `capsule_delete`, `feature_hint_seen`. requestId для повторов. Суммы и ответы клиента не являются доверенными. Поддержать lifecycle после родов и паузу сообщений.

POST `/api/auth/gamification/preferences`, GET `/api/auth/gamification/letters`, GET `/api/auth/stars`, POST `/api/auth/stars/purchase`. Существующий GET /points остаётся совместимым.

### access-ai

Согласовать с wallet единый счётчик купленных вопросов. Сначала free, потом paid; купленные не сгорают, расход paid <=6/10 в день и покупок <=2/1. Любое обращение, включая фото/файл, стоит 1 единицу (решение 2026-11-13); failed возвращает соответствующий запас ровно один раз; конкурентные запросы и смена курса не создают дополнительных дневных квот. Сохранить текущий формат quota для старых потребителей и добавить paidRemaining/paidDailyRemaining/freeRemaining, public maximum.

Серверные запреты закрытых будущих статей/описаний/видео должны действовать на прямые ссылки, списки, поиск, рекомендации Лары и полные исходные JSON. Календарь остаётся доступен. Существующие платные права и закрытие при ошибке GetCourse сохраняются. Legacy историю прав сначала анализировать, не закрывать неизвестные права.

### admin-notifications

`createGamificationSettings({pool,clock})` даёт `get()` с валидированными настройками и флагами, medicalApproved=false по умолчанию. wallet/daily берут настройки из этого объекта. Запретить обход медпроверки одним общим enabled. Изменения настроек и утверждения фиксируются с владельцем и временем.

`createGamificationNotifications({pool,...})` методы для пользовательского списка/прочтения/создания событий, preferences и opt-in push. Сигнатуры немедленно записать в handoff. По возможности создавать запись события в той же транзакции, что и награда. «Звёздочки» строятся из ledger, не зажигают красную точку; открытие колокольчика не читает чаты. Не рассылать ни одного production push при разработке. Нужные новые HTTP routes перечислить для access-ai; main worker wiring — для оркестратора.

### frontend

Создать единый клиент новых API, затем пользовательские действия с обработкой повторов, ошибок, смены аккаунта и server-derived возможностей. Состояния медицинских черновиков не показывать как опубликованный контент. Не вставлять технические слова о rollout/settings/schema в пользовательские экраны. Не менять визуальную основу без необходимости. Существующие страницы, нижняя навигация, мобильная ширина и авторизация сохраняются. Backend handoffs являются договором; если API ещё не готов, тестировать fixtures с точным тем же форматом, затем обязательно подтвердить интеграцию.
