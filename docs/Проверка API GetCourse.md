# Проверка API GetCourse

13 октября 2026 года. Проверка документации и доступного кабинета школы, без подключения интеграции.

## Результат

Возможности для связи аккаунта и чтения доступов есть в официальной документации. Получена публичная [схема Tech API](https://getcourse.ru/pl/postback/redoc/schema), HTTP 200, версия `1.0.0`; описание авторизации также сверено в [браузерной документации](https://getcourse.ru/pl/postback/redoc). Это подтверждение описанных методов, а не успешные запросы с ключами школы. В текущем меню профиля школы настройки аккаунта и API не показаны; ключи не создавались и не извлекались из существующих интеграций.

На момент исследования создание карточки GetCourse для бесплатных регистраций не было согласовано. 17 октября пользователь утвердил создание карточки после подтверждения email, в том числе для бесплатных пользователей; завершение регистрации ждёт успешного создания или связи карточки. Для аккаунтов выбрана отдельная PostgreSQL и Node.js на Timeweb. Реальные вызовы с ключами школы и побочные процессы ещё не проверены. Защищённый видеопросмотр остаётся отдельным решением.

## Подтверждённые методы

| Задача | Метод | Что использовать |
| --- | --- | --- |
| Найти существующего пользователя | `GET /pl/api/v1/user/get-fields` | По `email` или `userId`; получить ID для связи аккаунтов. |
| Проверить покупки | `GET /pl/api/v1/user/get-purchases` | По `email` или `userId`; возможен фильтр `productId`. |
| Прочитать доступные курсы | `GET /pl/api/v1/user/get-trainings` | По `email` или `userId`. |
| Прочитать группы пользователя | `GET /pl/api/v1/user/get-groups` | По `email` или `userId`. |
| Прочитать каталог школы | `GET /pl/api/v1/common/get-trainings` | Список тренингов. |
| Прочитать каталог групп | `GET /pl/api/v1/common/get-groups` | Для согласования соответствия групп и прав приложения. |

Источник таблицы — [публичная схема GetCourse](https://getcourse.ru/pl/postback/redoc/schema). Запросы выполняет сервер приложения. Email для поиска берётся из подтверждённого входа, а не из произвольного параметра браузера. Из ответа сохраняем только необходимые данные; полный профиль в журнал или базу приложения не копируем.

## Два вида API и ключей

**Tech API:** заголовок `Authorization: Bearer <ключ_разработчика>_<ключ_API_школы>`. Официальная документация отдельно описывает выдачу ключа разработчика через анкету и получение ключа школы у её представителей. Обычный ключ из раздела «АПИ» нельзя считать достаточным без проверки: [авторизация Tech API](https://getcourse.ru/pl/postback/redoc).

**Обычный API импорта:** `POST /pl/api/users`, действие `add`, секретный ключ в параметре `key`, данные JSON в Base64 в параметре `params`. Создание без покупки описано отдельно от заказов. При `system.refresh_if_exists=0` существующие данные не обновляются. `action=update` для групп заменяет их список; это неподходящий способ просто отметить источник регистрации. [API импорта](https://getcourse.ru/help/api).

Для чтения нужен доступ только к согласованным операциям. Запись пользователей понадобится, если школа подтвердит создание бесплатных карточек. Настройка подписок на события — отдельная операция, её права и последствия нужно проверить до подключения. Обычный ключ «чтение и запись» даёт широкие права; отдельного разрешения исключительно на создание карточки считать доступным нельзя: [права ключей](https://getcourse.ru/blog/1053682).

## Что схема ещё не доказывает

В покупке описаны `id`, `product_id`, `user_id`, `start_at`, `finish_at`, `period_type`, `is_actual`, `is_payed`, `state`, `updated_at`. `state` допускает `null`, его значения не перечислены; ID предложения в модели покупки не описан. Значение флагов, представление бессрочного доступа, заморозки и часовой пояс дат нужно подтвердить на реальных примерах. [Модель покупки](https://getcourse.ru/pl/postback/redoc/schema).

Метод `/set-uri` описывает события создания заказа, изменения его статуса и оплаты. Отдельные события изменения покупки, групп, заморозки и истечения доступа в этом перечне не перечислены. Это не доказывает отсутствие других механизмов: процессы GetCourse умеют отправлять callback по выбранному объекту. Покрытие нужных изменений в аккаунте школы требует отдельной проверки. [Схема событий](https://getcourse.ru/pl/postback/redoc/schema), [callback в процессах](https://getcourse.ru/blog/276215).

Для обычного Export API документирован общий предел 100 запросов за два часа, включая проверки готовности выгрузки. Это не подтверждённый лимит Tech API. Массовый экспорт не подходит для проверки каждого входа; лимиты Tech API и нагрузку существующих интеграций уточняем отдельно. [Ограничения экспорта](https://getcourse.ru/help/api).

17 октября повторно проверена [документация Import API](https://getcourse.ru/help/api#limits): создание новых пользователей ограничено месячной квотой тарифа; изменение существующих объектов эту квоту не расходует. Перед запуском бесплатной регистрации нужно проверить лимит, текущий расход и запас на месяц, а также скоростные ограничения. Это отдельный предел от Export API. В коде подготовлен импорт `add` с `refresh_if_exists=0`, без передачи групп, заказов и согласия на рекламу. Обработка реального ответа и письма школы требуют тестовой карточки.

В кабинете школы проверен отдельный продукт доступа к чату, который выдаёт вхождение в группу. Поэтому список тренингов сам по себе не описывает все права на чаты. Конкретное соответствие продуктов, групп, курсов и функций приложения школа ещё должна утвердить.

Наличие методов каталогов не подтверждает выдачу защищённых видеоссылок или сквозную авторизацию браузера GetCourse. Эти возможности здесь не проверялись и не являются результатом работы с перечисленными методами.

## Предлагаемый порядок проверки интеграции

Это план проверок после получения разрешённых ключей и тестовых примеров, а не реализованная функция.

1. Проверить авторизацию Tech API отдельными ключами на тестовом пользователе школы. Секреты вводятся только в серверное окружение либо передаются через согласованное защищённое хранилище; в переписку и документы их не включаем.
2. Прочитать пользователя по подтверждённому email и сохранить связь с его ID. Проверить форму ответа: схема допускает объект или массив; неоднозначное совпадение нельзя автоматически разрешать выбором первой записи.
3. Прочитать его покупки, тренинги и группы. Согласовать значение состояний и таблицу «продукт / группа → разрешённые функции». Наличие оплаченного заказа не заменяет проверку действующего доступа.
4. Создание бесплатной карточки утверждено 17 октября. Проверить новую регистрацию, повтор запроса, существующий email и влияние на школьные процессы и письма до включения живой интеграции.
5. Проверить каждый способ изменения покупки и доступа, доставку события и контрольную сверку. События могут повторяться или приходить с задержкой; актуальное состояние перечитываем, окончание по известной дате учитываем на сервере. Способ сверки и допустимую задержку ещё согласуем.
6. Проверить сбой GetCourse и правила временной работы приложения. Бесплатный аккаунт и платные права рассматриваем отдельно; неподтверждённый новый доступ не выдаём. Политику для уже выданного доступа при сбое требуется утвердить.

## Примеры, которые должен предоставить или проверить технический специалист

| Пример | Что проверяем |
| --- | --- |
| Существующий пользователь, действующая покупка | Совпадение ID и правильного продукта, срок и разрешённые функции. |
| Бесплатный пользователь без покупки | Создание карточки после подтверждения email без платных прав и дубликатов. |
| Покупка с будущим началом или истёкшим сроком | Доступ не открывается по одному факту оплаты. |
| Возврат, заморозка, ручное закрытие | Какие поля меняются, какое событие приходит и когда приложение узнаёт об изменении. |
| Продление и несколько покупок | Правильный выбор основания доступа при разных сроках и продуктах. |
| Изменение группы, через которую выдан чат | Учитывается согласованное право на чат, остальные группы не открывают функции автоматически. |
| Повтор и задержка события | Старое событие не возвращает доступ, который уже закрыт. |
| Потерянное событие или недоступность GetCourse | Контрольная сверка восстанавливает состояние по согласованным правилам. |

До реальных запросов нужны: подтверждение типа ключей и прав; лимиты Tech API; обезличенные ответы; расшифровка состояний, флагов и времени; фактический перечень событий по покупкам и группам. Конкретный запрос включён в [черновик ответа специалисту](Ответ%20техническому%20специалисту.md).
