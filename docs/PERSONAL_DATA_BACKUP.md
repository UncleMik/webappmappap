# Резервная копия данных приложения

Согласовано пользователем 27 октября 2026 в первом этапе переноса личных записей в PostgreSQL. Реализация в `deploy/backup.py` дополняет ежедневный набор копией базы входа `wep_pril_auth`: в ней находятся аккаунты, профиль, сессии, проверка курсов и новые личные записи. `articles.sqlite` включает статьи, недельные материалы, каталог и закрытый реестр ссылок на видео. `uploads.tar.gz` содержит файлы контента.

Задание `wep-pril-backup.timer` запускает скрипт в 03:15 UTC. Каждый набор находится в отдельной папке `/opt/wep_pril/backups/YYYYMMDDTHHMMSSZ/` и содержит `articles.sqlite`, `uploads.tar.gz`, `auth.pgcustom`, контрольные суммы в `manifest.json` и отметку `complete`. Все файлы остаются закрытыми для посторонних процессов сервера. Отметка создаётся только после успешной копии SQLite, создания архива, полного `pg_dump` и двух проверок чтения PostgreSQL-архива. Ошибка сохраняет неполную папку для диагностики; старые завершённые копии при ней не удаляются. Сохраняются семь последних завершённых наборов.

После установки скрипта сделать копию вручную и проверить восстановление в отдельную базу:

```sh
python3 /opt/wep_pril/deploy/backup.py
python3 /opt/wep_pril/deploy/verify-backup.py /opt/wep_pril/backups/YYYYMMDDTHHMMSSZ
```

Второй инструмент принимает только завершённый набор из каталога копий проекта, сверяет SHA-256 всех файлов и проверяет SQLite и архив изображений. Он создаёт новую PostgreSQL с именем `wep_pril_restore_check_<случайный идентификатор>`, восстанавливает архив одной транзакцией и сравнивает набор таблиц с составом архива. При нормальном завершении удаляет только эту временную базу после сверки её специальной метки. Если метка не совпала, оставляет базу для ручной проверки. Работающая `wep_pril_auth` не является целью восстановления или удаления.

SQLite и PostgreSQL создают внутренне согласованные снимки по отдельности; общей транзакции между ними нет. Обновления, произошедшие между их копированием, могут оказаться только в PostgreSQL. Проверка восстановления подтверждает чтение архива и состав таблиц, но сама по себе не воспроизводит все пользовательские сценарии после аварии.

Проверка восстановления не подтверждает возможность вернуть копию после потери всего сервера: семь наборов находятся на том же хосте. Отдельная площадка для копий и сроки хранения личных данных ещё требуют продуктового решения. Для возврата производства из архива нужен отдельный план остановки записи, восстановления SQLite, uploads и PostgreSQL как одного набора; описанные команды его не выполняют.
