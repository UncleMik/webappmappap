Рабочий каталог: `/opt/wep_pril` на сервере `129.101.119.250`.

## Каталоги сервера

```
/opt/wep_pril/
  backend/                  Node.js API и инструмент импорта
  data/articles.sqlite      тексты, названия, недели, ссылки на иллюстрации
  uploads/articles/         WebP с именами по хешу исходного файла
  uploads/articles/originals/ все исходные PNG, недоступные через HTTP
  uploads/weekly/          иллюстрации недель с именами по SHA-256
  backups/                  семь последних завершённых резервных копий
  deploy/                   systemd, nginx, Certbot, исходный импорт и отчёт
```

Код хранится в Git; база, картинки и сертификаты в Git не включаются.
Материалы в `docs/content/pregnancy-articles/` — архив исходного документа
и редакционных источников. Они не публикуются в Pages и не используются
в работающем интерфейсе. Рабочий источник статей — серверная база.

## API

- `GET /api/health` — состояние сервиса и число опубликованных статей.
- `GET /api/articles` — заголовки, недели, время чтения и картинки без текста.
- `GET /api/articles?week=27` — подборка выбранной недели.
- `GET /api/articles/pregnancy-001` — статья с текстовыми блоками.
- `GET /uploads/articles/<имя>.webp` — изображение.
- `GET /api/weekly-content` — материалы «Малыш» и «Мама», календарь по неделям 1–42 и пояснения к отдельным неделям.
- `GET /uploads/weekly/<SHA-256>.webp` — иллюстрация недели.

Списки и статьи кешируются на 60 секунд, поддерживают ETag. Картинки
кешируются на 30 дней: изменение оригинала создаёт новое имя файла.
Изображения загружаются лениво. Сжатие WebP сохраняет каждый пиксель
и размеры исходника, уменьшение разрешения не используется.

## Импорт и обновление

1. Подготовить JSON со статьями и картинки вне публичного репозитория.
   `tools/prepare-server-articles.py` проверяет архив против инвентаря Drive,
   сопоставляет названия и создаёт WebP с проверкой пикселей и SHA-256.
2. Создать резервную копию: `python3 /opt/wep_pril/deploy/backup.py`.
3. Загрузить картинки и JSON на сервер.
4. Импортировать:

   ```sh
   node /opt/wep_pril/backend/import-articles.mjs \
     /opt/wep_pril/deploy/import/articles.json \
     /opt/wep_pril/data/articles.sqlite /opt/wep_pril/uploads
   ```

Импорт выполняется одной транзакцией, сохраняет существующие статус и
правило доступа. Несопоставленные иллюстрации перечислены в отчёте импорта;
случайные картинки вместо них не назначаются. Изменённый контент доступен
без публикации кода фронта и перезапуска службы после истечения кеша.

## Эксплуатация

Недельный исходник находится в `backend/seed/weekly-content.json`, изображения —
в `backend/seed/uploads/weekly/`. Перед импортом скопировать изображения в
`/opt/wep_pril/uploads/weekly/`, сделать резервную копию и выполнить:

```sh
node /opt/wep_pril/backend/import-weekly-content.mjs \
  /opt/wep_pril/backend/seed/weekly-content.json \
  /opt/wep_pril/data/articles.sqlite /opt/wep_pril/uploads
```

Импорт проверяет наличие всех 42 недель каждого раздела, структуру данных и
наличие изображений до записи в базу. Все записи обновляются одной транзакцией;
ранее выставленные `draft` и `restricted` сохраняются. API отдаёт только
`published` + `public`. Изменения текста становятся доступны после 60 секунд
кеша API; новое имя иллюстрации соответствует новому содержимому файла.

Node.js 24, SQLite из `node:sqlite`, nginx и Certbot. Node.js слушает
только `127.0.0.1:3000`; наружу API отдаёт nginx по HTTPS.
Настройки запуска находятся в `deploy/`. Секретный ключ сертификата —
только `/etc/letsencrypt`, пароли в проекте не хранятся.

```
systemctl status wep-pril
journalctl -u wep-pril --no-pager -n 50
systemctl list-timers 'wep-pril-*'
```

Сертификат IP короткоживущий: обновление проверяется дважды в сутки,
после обновления nginx перечитывает сертификат. Резервная копия базы
через SQLite Backup API и архив всех картинок создаются ежедневно.
Копии на том же сервере защищают от ошибок обновления; внешнее резервное
хранилище пока не подключено.

Для восстановления: остановить `wep-pril`, сохранить текущую базу,
восстановить `articles.sqlite` и `uploads/` из одной завершённой копии,
выдать пользователю `wep-pril` чтение базы, запустить службу и проверить
API и статью на фронте. Рискованное восстановление предварительно согласовать.

Проверки: `node --test backend/test/*.test.mjs` из корня проекта.

## Вход по email — этап от 17 октября 2026

Согласованный сценарий и оставшиеся условия запуска находятся в
[плане регистрации](../docs/План%20регистрации%20и%20входа.md).

- Отдельный процесс `auth/main.mjs` слушает только `127.0.0.1:3001`.
  Сервис статей на 3000 и его SQLite не изменяются.
- `POST /api/auth/request` принимает email, возвращает непрозрачный запрос входа.
- `POST /api/auth/verify` проверяет код и создаёт/связывает карточку GetCourse.
- `POST /api/auth/complete` повторяет завершение после сбоя GetCourse по уже
  подтверждённому запросу в пределах первоначального срока кода. До успеха сессии нет.
- `GET /api/auth/session` читает текущую сессию; `POST /api/auth/logout` отзывает её.
- Сессия: случайный токен, в базе только SHA-256; cookie `__Host-school_session`,
  `Secure`, `HttpOnly`, `SameSite=Lax`, 30 дней с момента выдачи. Коды — HMAC с
  отдельным секретом, срок 5 минут, одноразовое завершение в транзакции.
- Действуют согласованные лимиты кода, дополнительные бюджеты отправки и
  общие ограничения запросов. IP сохраняется только как HMAC в короткоживущем ключе.
  Секреты, email и ответы провайдеров в журналы не выводятся.
- Очередь GetCourse хранится в PostgreSQL; повторный `add` использует
  `refresh_if_exists=0`, не передаёт группы и покупки. Семантику ответа и побочные
  письма/процессы школы требуется проверить на согласованной тестовой карточке.
- Истёкшие коды и счётчики очищаются в течение суток, истёкшие сессии — при
  очередной очистке. Неуспешная регистрация повторяется в фоне не более суток;
  после истечения подтверждения для входа всё равно нужен новый код.

Подготовка сервера после получения ключей и проверки процессов школы:

1. Проверить ресурсы и российское расположение сервера, место для PostgreSQL,
   закрытый порт БД, возможность восстановления и отдельные зашифрованные копии.
   Сначала сохранить текущие конфигурации и базу статей. Нынешний сервис статей
   имеет лимит 192 МБ; его нельзя считать бюджетом всего приложения.
2. Создать отдельного системного пользователя `wep-pril-auth` без shell-входа,
   отдельную БД и пользователя PostgreSQL. Выдать ему чтение кода, не давать
   доступ к базе/копиям статей; файлы секретов загружает systemd от root. Заполнить
   `/etc/wep-pril/auth.env` по [образцу](../deploy/auth.env.example); файл
   `root:root`, `0600`, секреты вводить на сервере или через защищённое хранилище.
   Секрет HMAC — криптографически случайные 32 байта или больше. Не менять его
   без плана ротации: от него зависят активные коды и ключи ограничений.
3. Установить зависимости `npm ci --omit=dev`, применить миграцию
   `node auth/migrate.mjs` с `AUTH_DATABASE_URL` в окружении, без URL в аргументах.
   Запускать миграции под отдельным владельцем, сервису выдать только необходимые
   права чтения/записи таблиц и последовательностей.
4. Настроить [systemd](../deploy/wep-pril-auth.service) и маршрут
   [nginx](../deploy/nginx-auth-location.conf) **только** на домене приложения.
   Проверить `nginx -t` перед перечитыванием. Штатная конфигурация статей не заменяется.
5. По решению от 18 октября использовать существующий ключ основного аккаунта
   Unisender 8376474 и сохранённый в нём шаблон; отдельный проект не нужен.
   Проверить доставку, отключённый трекинг, Reply-To и квоты. Лимит 500 писем
   в сутки и ссылку отписки сохраняем; `UNISENDER_TRANSACTIONAL_APPROVED=false`.
   Обход отписок и жалоб не включаем; повторное получение кодов после отписки
   уточнить у провайдера до публичного запуска.
6. Проверить GetCourse: ключ импорта, квоту новых пользователей, существующий email,
   отсутствие перезаписи групп и покупок, процессы и нежелательные рассылки.
   Для первого этапа входа Tech API чтения покупок не нужен; платные права отдельно.
7. Согласовать и проверить сроки хранения/удаления аккаунтов, резервные копии,
   документы бесплатной регистрации и сведения ответственного за персональные данные.
8. Только после проверки интеграций включать `AUTH_ENABLED=true` и проверять
   реальный вход на HTTPS, повторный вход, выход, телефоны и PWA.

На проверенном сервере npm находится внутри комплекта Node.js, но не в `PATH`:
`node /opt/wep_pril/deploy/node-v24.21.0-linux-x64/lib/node_modules/npm/bin/npm-cli.js`.
Для подготовки зависимостей используется `ci --omit=dev --ignore-scripts --no-audit --no-fund`
в отдельной папке подготовки. Проверки с настоящей PostgreSQL не требуют установки
PGlite: эта зависимость теперь загружается только для локального варианта в WASM.

`npm test` запускает SQL и HTTP-проверки. Без `AUTH_TEST_DATABASE_URL` используется
PostgreSQL в WASM (PGlite) с последовательным соединением: это проверка логики,
**не** проверка реальной конкуренции PostgreSQL и не нагрузочный тест сервера.

Для проверки настоящей PostgreSQL передать `AUTH_TEST_DATABASE_URL` в окружении;
имя отдельной тестовой базы обязано заканчиваться на `_test`. Тесты создают
собственную схему и удаляют только её. Производственные базы не использовать.

`node test/auth-load.mjs` требует эту отдельную PostgreSQL. Профиль: 1000 сессий,
по одному запросу на пользователя раз в 30 секунд, длительность 60 секунд
(можно задать `AUTH_LOAD_SECONDS=900`). Письма и GetCourse не вызываются.
Это проверка слоя сессий; видео, чаты, ИИ и вся нагрузка приложения сюда не входят.
Порог задержки и длительность приёмки утверждаются до проверки готовности.

Предварительный серверный прогон 17 октября: 60 секунд, 2000 запросов, 0 ошибок,
p50 2 мс, p95 4 мс. Это HTTP по localhost с PostgreSQL, без nginx/TLS и реальной
почты/GetCourse. Журнал: `/opt/wep_pril/deploy/auth-load-check.log`. Unit завершился
успешно; тестовых схем после очистки 0, рабочих аккаунтов/сессий 0. Это не приёмка
всего приложения на 1000 пользователей и не основание обещать такую ёмкость чатов,
ИИ или видео. Регулярные резервные копии PostgreSQL, внешнее хранение и проверка
восстановления остаются условиями публичного запуска; копия статей их не заменяет.

Изолированный браузерный стенд `test/fixtures/auth-browser.mjs` запускается только
при `AUTH_BROWSER_QA=1`, слушает localhost и использует синтетические данные.
Он не отправляет письма и не обращается к GetCourse; в production его не запускать.
